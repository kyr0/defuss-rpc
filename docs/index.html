Call server-side functions and classes as if they ran client-side

Dates come back as Dates Generators stream to for await Uploads report their progress No framework needed on Bun

defuss-rpc exposes server-side functions and classes as a fully typed, async client API, built from the server's schema at runtime. defuss-dson encodes every argument and result, so Date, Map, Set, BigInt and typed arrays arrive intact. Calls, sequential or parallel, are plain HTTP and JSON; event streams are NDJSON you read with for await; files travel as raw bytes, uploads with progress. On Bun it needs nothing else: Bun.serve is the default and answered the most calls with the least memory. Express, bunway, Vite and Astro are optional.

Typed from your server code

getRpcClient<typeof RpcApi>() types every call from the server's own export. No schema language, no generated stubs that go stale.

Generators stream

An async * method sends each yield as an NDJSON frame the moment it happens; break on the client stops the generator on the server.

Types JSON loses

DSON carries Date, Map, Set, BigInt and every typed array, plus undefined, NaN, ±Infinity and -0, as arguments and as results.

Files of any size

Uploads stream to disk with SHA-256, gzip and live progress, and resume after a dropped connection; streaming handlers read them in bounded chunks.

Hooks at both ends

Server guards reject calls with 403 before they run; client hooks add auth headers, metrics and logging around every call.

Your server framework

rpcRoute maps a Request to a Response for Bun.serve and Astro routes; ExpressRpcServer runs it on Bun.serve by default, or on Express (Node.js and Bun) or bunway (Bun) when you import their provider.

Get started

Define, serve, call

Three files. Each one below is a file of examples/, and the end-to-end test runs every one of them against the published package, on Node.js and on Bun.

  1. 01

    Define the API as classes and modules

    Export one object of namespaces and its type. A class gets a fresh instance per call; a module is shared.

  2. 02

    Serve it

    ExpressRpcServer adds CORS, gzip, body limits and a health route. Without a provider it runs on Bun.serve at port 63920: the default, with the most calls per second and the least memory (Performance). Import a provider only on Node.js or for a framework's routes and middleware. A Bun.serve you already run can mount rpcRoute itself.

  3. 03

    Call it, typed

    The client fetches the schema once per endpoint and builds callers for every method. The comments show what the e2e test sees printed.

Performance

Stay on the default

Of every ExpressRpcServer setup, the default on Bun.serve answered the most small calls and needed the least memory, idle and under load, in two runs of make bench. Choose a provider for Node.js or for a framework's middleware, not for speed.

  • 63,926calls per second on the default (64,195 in run 1). bunway: 53,315. Express on Node.js: 32,784.
  • 0 / 2 mscall latency, p50 / p99. bunway: 1 / 2. Express on Node.js: 1 / 3.
  • 29 MiBmemory (RSS) of the idle server. bunway: 38. Express on Node.js: 98.
  • 59 MiBmemory under small calls. bunway: 70. Express on Node.js: 243.

Reading the numbers

What the benchmark measured, and where the default does not lead.

How was it measured?

On 2026-11-02, on an Apple M5 Max with Node.js 26.11 and Bun 1.4.3: 5 s per scenario, 64 connections, autocannon on the same machine at a load average of 4.4 and 6.3 before the two runs. Every column except run 1 comes from run 2.

Where does the default not lead?

Files: every server moved 1.2 to 1.6 GiB/s up and 8.2 to 8.6 GiB/s down, and Express on Node.js downloaded 1 to 3 percent faster than the default in both runs. The memory peak while moving files, 340 to 460 MiB for every server, did not rank the servers the same way in both runs; Express on Bun had the lowest.

Why is rpcRoute faster than the default?

It is the baseline: rpcRoute in a bare Bun.serve. The default adds CORS, routing, body reading and the size limit, and that work is the gap.

Can I measure it myself?

make bench runs every scenario on your machine. The README has the full table, with uploads and downloads.

Protocol

How a call travels

Plain HTTP with four body formats: DSON for calls, NDJSON for generators and upload answers, raw bytes for files, Server-Sent Events for upload progress. Without ExpressRpcServer (rpcRoute in your own Bun.serve or an Astro route) your server takes the place of the HTTP layer.

The encoding on each layer

What each layer reads and writes, per kind of request, from your code down to your API.

  • Calls

    application/json Sequence

    Your code and the client
    Typed values: Date, Map, Set, BigInt, typed arrays.
    Wire (HTTP)
    POST /rpc with DSON text as application/json.
    HTTP layer
    CORS; inflates gzip and deflate bodies; 413 above jsonSizeLimit; gzip above 1 KiB.
    rpcRoute and your API
    DSON.parse gives the arguments, DSON.stringify the answer.

  • Generators

    application/x-ndjson Sequence

    Your code and the client
    for await over the values.
    Wire (HTTP)
    One DSON frame per line: each yield, then return or error.
    HTTP layer
    gzip, flushed after every frame.
    rpcRoute and your API
    The generator is pulled once per read.

  • Uploads

    application/octet-stream Sequence

    Your code and the client
    An async iterator of sending, receiving and complete.
    Wire (HTTP)
    POST /rpc/upload: raw bytes, gzip, with the headers
    • X-Upload-Handler
    • X-Upload-Id
    • X-Original-Size
    • X-Upload-Offset
    • X-Original-Filename
    Progress as Server-Sent Events with JSON data; the answer as NDJSON.
    HTTP layer
    No size limit; progress events are never compressed.
    rpcRoute and your API
    The handler runs after the last byte, with the bytes or a chunked stream.

  • Downloads

    raw bytes Sequence

    Your code and the client
    { data, filename, sha256 }, or a Blob.
    Wire (HTTP)
    GET /rpc/download: raw bytes with Content-Disposition (RFC 6266) and X-File-Sha256.
    HTTP layer
    Passed through, never compressed.
    rpcRoute and your API
    The handler returns bytes or a stream, plus fileMeta.
Vite & AstroOptional

The dev server starts the RPC server

You need neither. defuss-rpc runs on its own, on Bun.serve or a provider, as shown above, and depends on neither. Add one of these packages only when your app already runs on Vite or Astro and vite dev or astro dev should start the RPC server for you.

defuss-rpc-vite runs an ExpressRpcServer beside the dev server (on Bun without a provider, port 63920) and tells the client where it is through virtual:defuss-rpc, so getRpcClient() needs no options.

Streaming and types

Generators become for await

A generator method answers with application/x-ndjson: one DSON frame per yield, then a return frame, or an error frame the client throws. The server pulls the next value only when the client reads, and a break runs the generator's finally.

On the wire

Each NDJSON line is DSON's compact encoding of { type, value }, which the client decodes with DSON.parse. A method that is not a generator answers with one DSON body.

Types JSON loses

DSON encodes every argument and result, so a Date stays a Date, a Map a Map and a BigInt a BigInt, and a typed array keeps its bytes.

Files

Uploads and downloads with a hash on every byte

An upload is written chunk by chunk to a temp file while the server computes SHA-256; the handler runs when the last byte arrived. Pass a known uploadId and the client asks the server how far it got and sends only the rest.

In a browser page

The same calls from a page: progress for a progress bar, and the file back as a Blob for an object URL or a save link.

The events of upload()

upload() yields these events to for await. uploadComplete() skips the progress stream and returns the fields of complete.

  • sending

    Node.js and Bun: per chunk of the streamed body. Browsers: once, after the buffered body was sent.

    • bytesSent
    • totalBytes
    • percent

  • receiving

    Where EventSource exists (browsers): the bytes the server has stored, from its progress stream.

    • bytesReceived
    • totalBytes
    • percent

  • complete

    Once, at the end, with the handler's return value.

    • result
    • uploadId
    • bytesReceived
    • sha256
    • durationMs
Hooks

Guards before, hooks after

Server guards see the namespace, method, arguments and the raw Request; an explicit false answers 403 before the method runs. Client hooks wrap every call: a guard can stop it, response and result hooks observe it.
